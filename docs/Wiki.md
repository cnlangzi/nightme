# Wiki

LLM-driven repository wiki. Output is `<cwd>/wiki/` (content) + `<cwd>/wiki.yml` (metadata). Index format follows the [llms.txt v1.0](https://llmstxt.org) spec; per-module pages follow the [DeepWiki](https://deepwiki.com) component-page convention.

A single `/wiki` slash command keeps the structure in sync with the source tree — one run scaffolds on a fresh repo, subsequent runs reconcile the module roster against the current code.

## 1. Motivation

LLM coding agents working on a large repository need a pre-distilled map of the codebase before editing. Reading raw source to extract intent burns token budget and risks missing cross-cutting conventions spread across files.

`wiki/` answers the questions an agent asks first when assigned a task:

- What is this package? (`## Public Surface`, `## Key Flows`)
- How does it fit with the rest? (`wiki/architecture.md`, cross-module links in `llms.txt`)
- What conventions must I follow? (`## Cross-cutting Patterns`)
- What design choices should I not undo? (`## Non-obvious Choices`)

This complements `tokensave` and `codegraph`, which answer structural queries ("who calls X?"). The wiki answers narrative queries ("what is X and why does it exist").

## 2. Scope

### In scope

- `/wiki` slash command — single command, idempotent across runs
- `<cwd>/wiki/` directory + `<cwd>/wiki.yml` at repository root (sibling, not under `.nightme/`)
- llms.txt v1.0-compliant index with project name, Architecture, Modules, Reference sections
- DeepWiki per-module pages with 5 fixed sections
- Exclusion driven by `<cwd>/.gitignore` (re-uses the user's existing ignore file)
- Dot-prefix default skip with `wiki.yml.include` opt-in for hidden paths

### Out of scope

- LLM content generation (current `moduleDocStub` fills only `## File Layout` and the `<!-- sources -->` footer; other sections are `[TBD]` placeholders)
- Git operations (`/wiki` does not commit; user commits manually)
- Wiki file deletion when a module is removed (file preserved on disk for audit)
- Per-language provider abstraction (the wiki treats all languages uniformly; language recognition is the LLM's job)
- Hand-written narratives (all content is either template-rendered or LLM-generated)

## 3. File layout

```
<cwd>/
├── wiki.yml
└── wiki/
    ├── llms.txt
    ├── architecture.md
    ├── glossary.md
    └── modules/
        └── <slug>.md
```

`<slug>` is the package basename — `internal/command/gtw` → `gtw.md`. The full path lives in `wiki.yml.modules[].path` for disambiguation.

### 3.1 `wiki/llms.txt`

Format: [llms.txt v1.0](https://llmstxt.org). One H1 (project name) followed by H2 sections of markdown links.

```markdown
# <project-name>

## Architecture

- [Architecture Overview](./architecture.md)

## Modules

- [gtw](./modules/gtw.md)
- [review](./modules/review.md)
- ...

## Reference

- [Glossary](./glossary.md)
```

Removed modules are not listed. Module descriptions are omitted until the LLM content path populates them.

### 3.2 `wiki/modules/<slug>.md`

Format: DeepWiki `page_type=component`. Five fixed sections in order: Public Surface, File Layout, Key Flows, Cross-cutting Patterns, Non-obvious Choices.

Stub template (current):

```markdown
# <slug>

> Stub generated by `/wiki` (no LLM). Replace with LLM content on the next agent-driven run.

## Public Surface

[TBD — exported types and functions from this package]

## File Layout

| File | Lines |
|---|---|
| `a.go` | 42 |
| `b.go` | 17 |

## Key Flows

[TBD — main user-facing flows in this package]

## Cross-cutting Patterns

[TBD — patterns observed across this package's source]

## Non-obvious Choices

[TBD — design decisions not obvious from reading the code]

<!-- sources -->
- internal/foo/a.go
- internal/foo/b.go
```

The `## File Layout` table and `<!-- sources -->` footer carry real data the LLM can build on; the other sections are `[TBD]` markers.

### 3.3 `wiki/architecture.md`

```markdown
# Architecture

## Components

## Main Flows

## Module Dependency Graph

## Key Invariants
```

Empty sections filled in by the future LLM path.

### 3.4 `wiki/glossary.md`

```markdown
# Glossary

| Term | Definition | Source |
|---|---|---|
```

Empty 3-column table.

### 3.5 `wiki.yml` schema

```yaml
version: 1                    # schema version; bump on backwards-incompatible shape change
last_commit: null             # sha of last /wiki run that produced content (future)
agent: null                   # default LLM agent recorded on first successful run (future)
include: []                   # force-include paths (see §5.3)
modules:
  - path: internal/command/gtw
    file: gtw.md
    last_sha: null            # sha of last LLM write (null = stub-eligible)
    # removed: true           # present when path is no longer in source
```

Pointer fields distinguish "absent" from "explicitly null" on round-trip.

## 4. The `/wiki` command

A single command with no subcommands. Idempotent — running it on a fresh repo scaffolds; running it on an existing wiki reconciles.

### 4.1 Flag

```
/wiki [-a <agent>]   sync <cwd>/wiki/ + <cwd>/wiki.yml with the source tree
```

`-a` / `--agent` is reserved for the future LLM content path. Current stub mode accepts and ignores it.

### 4.2 State machine

| `wiki.yml` | `wiki/` | Action |
|---|---|---|
| absent | absent | Fresh scaffold (`Scaffold`) |
| present | present | Reconcile existing state |
| mixed (one present, other absent) | | Refuse with `ErrWikiHalfState` |

Half-state is ambiguous (which side is canonical?). Silent recovery risks losing either metadata or content, so the user is asked to delete one side and retry.

### 4.3 Reconcile algorithm

For each path in `<cwd>/.gitignore`-filtered source tree:

| yml.modules state | Source state | Action |
|---|---|---|
| absent | present | Append new entry, write skeleton |
| present (live) | present | Keep entry, refresh `file` field |
| present (live) | absent | Set `removed: true` |
| present (removed) | present | Un-mark removed, refresh `file` field |
| present (removed) | absent | Stay removed (idempotent) |

Live modules come first in `wiki.yml` (sorted by path), followed by removed modules.

### 4.4 Content regeneration

For each live module:

- `last_sha` is null → write `moduleDocStub` (overwrite existing stub)
- `last_sha` is non-null → preserve (LLM wrote content here; don't touch)

Removed modules: do not touch the wiki file (preserve on disk).

`llms.txt` is regenerated from the live module list each run.

### 4.5 Reply format

```
✅ /wiki

Added 2 module(s):
• internal/cli
• internal/configs

Marked 1 removed (wiki files preserved):
• internal/deprecated

Wrote 3 stub(s).
Preserved 5 module file(s) (LLM content kept).
```

Counts and short bullet lists. Per project convention, the post-summary keeps decision info, not raw file lists (per AGENTS.md §1 — user-facing replies stay lean).

## 5. Architecture

### 5.1 Package layout

```
internal/command/wiki/
├── args.go       parseWikiArgs (-a/--agent)
├── cmd.go        Factory / Spec / Handle
├── sync.go       Sync() orchestrator + reconcile + runWiki
├── discover.go   discoverModules(cwd)
├── ignore.go     ignoreFilter + .gitignore parser + wiki.yml.include reader
├── skeleton.go   moduleDocSkeleton / moduleDocStub + llms.txt renderer
├── storage.go    Scaffold() (fresh path) + atomicWrite
├── yaml.go       wikiYml struct + parseWikiYml / encodeWikiYml
└── cmd_test.go
```

The slash command is registered via `command.RegisterBuilder` in `cmd.go`'s `init()` and picked up by the runtime orchestrator.

### 5.2 Module discovery

`discoverModules(cwd)` walks the directory tree. A directory becomes a module when:

- It survives the ignore filter (see §5.3)
- It contains at least one non-test, non-hidden file (Go: at least one `*.go` file excluding `*_test.go`)

Leaf rule: a directory that qualifies as a module is **not** recursed into. Sub-packages are documented inside the parent's `## File Layout` section, not as separate wiki pages. This matches the AGENTS.md §3 grouping (e.g. one module per `internal/bridge/<impl>` rather than per file).

### 5.3 Ignore system

Three-layer filter, applied in order:

1. **Built-in**: `wiki/` only (self-recursion guard; cannot be overridden)
2. **User `.gitignore`**: any path matched by the user's `<cwd>/.gitignore` is skipped
3. **Dot-prefix**: any path component starting with `.` is skipped
4. **`wiki.yml.include` opt-in**: an exact match in `wiki.yml.include` exempts the leading dot-component, allowing the walker to descend one level. Nested hidden directories (`.github/.private`) require their own include entry.

The gitignore parser supports literals, glob (`*` `?` `[abc]`), anchored patterns (`/foo`), dir-only patterns (`foo/`), and negation (`!foo`). Nested `.gitignore` files in subdirectories are out of scope for v0.

`wiki.yml.include` semantics are exact-match, not recursive. `include: [.github]` exempts `.github/` and the walker then re-evaluates each child (`.github/workflows` is normal, `.github/.private` is still hidden).

### 5.4 Module naming

Wiki file name is the module's basename: `internal/command/gtw` → `gtw.md`. Conflicts (two modules with the same basename) are out of scope for v0; users can disambiguate via `.wikiignore` or by adding include entries that rename.

## 6. Decisions

### Wiki lives at `<cwd>/wiki/`, not `<cwd>/.nightme/wiki/`

`<cwd>/.nightme/` is for runtime-emitted, repo-local config (mirrors `~/.nightme/gtw.yml`) — optionally committed, freely regenerated. `<cwd>/wiki/` is a first-class repo artifact, like `README.md` or `go.mod`: tracked, evolved, reviewed in PRs.

### `wiki.yml` is a sibling of `wiki/`, not inside it

`<cwd>/wiki.yml` is the operator-facing state file (machine-readable). Keeping it outside `<cwd>/wiki/` makes "delete the wiki" a single `rm -rf wiki/` without losing the module roster.

### `.gitignore` drives exclusion

The user's `.gitignore` already encodes "what should be preserved as part of the project." That semantic matches the wiki's "what should be documented." Reusing it eliminates a parallel `.wikiignore` file and the divergence risk that comes with two ignore lists.

### One `/wiki` command, no subcommands

`init` and `update` collapsed into one command because the distinction blurred once `init` became idempotent — running `init` to reconcile was already "init + regenerate stubs." Splitting into two commands added a half-state the user had to remember to avoid. The merged shape matches how users think: "I changed code → I run `/wiki`".

### Stub mode does not call an LLM

`moduleDocStub` fills `## File Layout` (real data) and `<!-- sources -->` (real paths) with placeholders for the rest. This validates the read-yaml → walk-modules → write-files pipeline before plugging an LLM call into the per-module slot. The LLM path replaces one function (`moduleDocStub`) when it lands.

### Removed modules' wiki files are preserved

When a module disappears from source, `wiki.yml` marks it `removed: true` and the wiki file stays on disk. The wiki file may be referenced from PR descriptions, commit messages, or external `llms.txt` consumers — silent deletion would break those references. Users `git rm` the file when ready.

### `last_sha` gates content overwrite

Modules with `last_sha: null` (stub or never-written) are overwritten each run. Modules with non-null `last_sha` (LLM wrote content) are preserved. The `last_sha` field is the LLM-path's commit marker; v0 leaves it null everywhere and naturally overwrites stubs each run.

## 7. Open items

- **LLM content path**: per-module agent dispatch via `agent.Builtins.RunOnce`. The prompt template, source-citation enforcement (`[file:line]` per DeepWiki), and `last_sha` update on commit are unbuilt.
- **Git operations**: optional `git add` + `git commit` after `/wiki` completes. User commits manually today.
- **Per-language prompts**: future providers can specialise the module prompt per language. v0 sends a language-agnostic prompt.
- **Wiki file deletion**: no automatic `git rm` of removed-module wiki files. User opt-in via `git rm wiki/modules/<slug>.md` after manual review.
- **Nested `.gitignore`**: the parser reads only `<cwd>/.gitignore`. Sub-directory `.gitignore` files are ignored.
- **Multi-collision names**: two modules with the same basename produce a wiki-file name clash. Not handled in v0.
